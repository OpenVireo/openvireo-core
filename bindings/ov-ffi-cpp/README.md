# ov-ffi-cpp

The C++17 binding of the openvireo-core facade, made with [cxx](https://cxx.rs). The desktop (Qt) links it as
`libovcore` and includes `<ovcore.h>`.

## Getting it

Pick one:

- **Prebuilt package:** `cargo xtask cpp [--target <triple>]...` writes a CMake package to
  `target/ovcore-cpp/<target>/`. Without `--target` it builds `universal-apple-darwin` on macOS (arm64 + x86_64,
  joined with `lipo`) and the host triple elsewhere. The release targets are `universal-apple-darwin`,
  `x86_64-pc-windows-msvc`, `aarch64-pc-windows-msvc`, `x86_64-unknown-linux-gnu` and
  `aarch64-unknown-linux-gnu`. Each one needs `rustup target add <triple>` and a C++ compiler for that target.

  ```cmake
  find_package(OpenVireoCore 0.0 REQUIRED)        # -DOpenVireoCore_DIR=<pkg>/lib/cmake/OpenVireoCore
  target_link_libraries(app PRIVATE OpenVireoCore::ovcore)
  ```

  The imported target brings the include directory, C++17 and the system libraries rustc reports
  (`--print native-static-libs`). `smoke/` is the acceptance test for the package.
- **From source with Corrosion,** as the desktop does: see `example/CMakeLists.txt`. Corrosion runs cargo. When
  `OV_CXX_INCLUDE_DIR` is set, `build.rs` exports the headers there. Corrosion v0.6 builds one Rust target per
  configure, so a universal macOS app uses the prebuilt package (or one configure per arch, then `lipo`).
  **On aarch64, pass `CARGO_TARGET_<TRIPLE>_RUSTFLAGS=--cfg aes_armv8`** (the example does): Corrosion runs cargo
  outside this repo, so `.cargo/config.toml` isn't read, and without the cfg AES-KDF runs in software (~30x slower).

Both paths build for macOS 11.0 and later unless `MACOSX_DEPLOYMENT_TARGET` / `CMAKE_OSX_DEPLOYMENT_TARGET`
says otherwise.

## Header layout

```text
include/ovcore.h                         include this
include/ov-ffi-cpp/include/ovcore.h      ov::Error, ov::call(), ov::wipe()
include/ov-ffi-cpp/include/host.h        the Host interfaces you implement
include/ov-ffi-cpp/src/lib.rs.h          generated by cxx: records, enums, handles, functions
include/rust/cxx.h                       cxx runtime (rust::String, rust::Vec, rust::Box, ...)
```

## Design

### Threading: blocking calls plus a CancelToken

Every facade call that is `async` in Rust (network, KDF, Host I/O) is a **blocking** C++ call. It runs the
core future to completion on the calling thread with `futures::executor::block_on`, and it takes an
`ov::CancelToken`. The other choice was callback-based completion. Blocking calls won for these reasons:

- **The core does no I/O of its own.** Every await ends in a Host call, and the C++ Host methods are synchronous.
  So there is nothing to drive in the background, and no Rust runtime or thread pool sits inside `libovcore`.
- **Qt already has the worker side.** The desktop calls the core from `QtConcurrent::run` / a `QThreadPool`
  task and gets the result back with a `QFutureWatcher` or a queued signal. A callback API would need the same
  thread hop plus lifetime rules for callbacks that outlive their caller.
- **Cancellation stays simple.** Keep `token->clone()` on the GUI thread and call `cancel()` on it. The core
  checks the token between steps. The edge also races the call against `CancelToken::cancelled()`, so a pending
  core future is dropped and the call returns `aborted` right away. A call made with a token that is already
  cancelled returns `aborted` without starting.
- **Host callbacks run on the caller's thread.** That thread is the worker that made the core call, never a
  hidden Rust thread. This keeps Qt's thread-affinity rules easy to follow. (A `QNetworkAccessManager` transport
  runs a local `QEventLoop`, or hands the request to a network thread and waits.)

Never call a blocking function on the GUI thread. The handles (`rust::Box<ov::Client>`, `ov::Account`,
`ov::Vault`, ...) are `Send + Sync` in Rust, so several workers may share one handle (pass it by reference).

### Host

`include/host.h` declares one pure-virtual class per Host trait: `HttpTransport`, `ByteStream`, `SecureStore`,
`BlobCache`, `Clock` and `LogSink`. `SecureStore::delete` is named `remove` because `delete` is a C++ keyword.
Pass them to `ov::new_client()` as `std::unique_ptr`. Their rules:

- They must be thread-safe, because the core may call them concurrently.
- Transport failures go in `TransportFailure{kind, message}`, mapped to `TransportError`. Any other failure is
  thrown. A `what()` that starts with a wire code and `": "` (for example `"forbidden: keychain locked"`) keeps
  that code. Anything else becomes `internal`.

### Errors and panics

Every bridged function catches panics and returns `OvError{code: internal}`. The facade's `todo!()` stubs
behave like this too, until W2-A fills them in. A failure throws `rust::Error` with the text
`"<wire code>: <message>"`. The full `OvError` (code, message, status, retry-after, details JSON, server code)
is saved for the calling thread. Wrap calls in `ov::call([&]{ ... })` to get an `ov::Error` that carries all
of it:

```cpp
try {
    auto vaults = ov::call([&] { return account->vaults(*cancel); });
} catch (const ov::Error &e) {
    if (e.code() == "plan_limit") { /* e.info().details is JSON */ }
}
```

### Records

Records cross as flat shared structs. cxx shared structs can't hold `Option`, so:

- `Option<String>` is an empty string.
- Other options are a `has_x` flag plus a value.
- Enums are cxx shared enums. A value C++ made up (outside the declared ones) is rejected with
  `invalid_request`.

Secrets (`password`, `secret_key`, `auk`, field values, `.kdbx` bytes) cross as `rust::Vec<uint8_t>`. Inputs
move into the core, which wipes them. The caller wipes outputs with `ov::wipe()`.

## Coverage

Wave 1 bridges the pipeline and the paths the desktop needs first. The rest of the facade (342 public methods,
see `docs/api-coverage.md`) uses the same patterns and is a follow-up once W2-A implements the bodies and
W3-ID says what the desktop calls.

| Area | Bridged |
|---|---|
| Free | `version`, `take_last_error`, `sha256`, `hkdf_sha256`, `aead_encrypt`/`aead_decrypt` (XChaCha20-Poly1305), `argon2id` (32 bytes), `random_bytes` |
| `CancelToken` | `new_cancel_token`, `clone`, `cancel`, `is_cancelled` |
| `OvClient` → `ov::Client` | `new_client`, `discover`, `connect`, `remembered_accounts`, `forget_remembered`, `session_state`, `has_pending_edits` |
| `Account` | `server_config`, `is_offline`, `is_signed_in`, `is_unlocked`, `user_id`, `email`, `login`, `submit_totp`, `unlock`, `lock`, `sign_out`, `vaults`, `open_vault`, `subscribe` |
| `LoginStep` / `TotpChallenge` | `needs_totp`, `challenge`, `take_unlocked`; `attempt` |
| `Vault` | `vault_open_local`, `vault_create_local`, `save_local`, `id`, `name`, `etag`, `is_offline`, `is_read_only`, `entries`, `groups`, `read_field`, `write_field`, `sync`, `export_kdbx` (all groups) |
| `EventStream` | `next` (`kind == Closed` for the end), `reconnect`, `close` |
| Host | all six traits |

Not bridged yet: register and recovery, settings, sharing and orgs, share links, plans, service accounts,
self-hosted sync, TOTP helpers, the other `Vault` edit and history methods, and `Account::signed_out`.

## Tests

- `cargo test -p ov-ffi-cpp`: the edge (panics, error fields, cancellation), conversions and primitives.
- `smoke/`: builds against the `cargo xtask cpp` package. It calls `version()` and `sha256("abc")`, and
  checks an OvError through `ov::call`, a panicking stub coming back as `internal`, and a cancelled call
  coming back as `aborted`.
- `example/`: the Corrosion build of the same core.
